# briqyard review, 2026-10-20

Scope: briqyard `main` at e1f4f2e (daemon, init, fleet, hack/) and the briq provider branch
`feat/briqyard-provider` (PR #250) against the monorepo's `CLAUDE.md`. Read-only; every finding
below was confirmed in the code unless marked "plausible".

## Verdict

The shape is right. The daemon is one `Manager` with a per-machine lock, records written last and
atomically, orphans swept at start, a proper jailer, a config drive instead of a mounted guest
filesystem, an image extractor that resists symlink escapes, and an ingress that is provider-free
on the briq side. The fleet is a thin forwarder with pure placement logic. Nothing here is a
Lima trick dressed as a feature: the Mac-specific bits live in `hack/config.dev.yaml` and
`hack/vm.sh` only. The foundation is sound enough to put on real servers after a short list of
fixes.

The three things to fix first:

1. **The host's ingress is a public, unauthenticated entry to every tenant** (finding B1). The
   daemon binds every TCP endpoint on `0.0.0.0` and the bootstrap writes `listen: 0.0.0.0:7420`.
   On a Scaleway or OVH server with a public address, anyone on the internet can connect to a
   `private` briq's port, bypassing the router's token check, and the plain-HTTP API is reachable
   with a sniffable bearer. The clean version: the daemon's API and ingress listen only on a
   private interface (WireGuard between the router and the hosts), and the daemon refuses to
   start with a public ingress bind unless told it is behind a firewall.

2. **Lifecycle transitions run inside the HTTP request future and are cancelled when the client
   hangs up** (finding B2). A `create` whose caller times out (the provider gives it 130 s; a
   first image pull can take longer) leaves the image build's `Notify` entry stuck so every later
   create of that image waits forever, or a Firecracker running with the machine still
   `starting`. The clean version: every transition is a spawned task (per-machine queue), the
   handler awaits its result; a disconnect never unwinds a transition.

3. **A boot failure caused by the image is reported as a 500 and read by the control plane as
   "provider unavailable"** (finding E1 / B3). `start_entry` returns `MError::Other` for "the
   guest did not come up" and "exited during boot"; the provider turns every 5xx into
   `ProviderUnavailableError`, so the reconciler retries a create that will fail the same way and
   the failure is logged as ours, not the caller's. The clean version: a machine that was
   processed and ended in `error` answers 409/422 `boot_failed` with the state; the provider maps
   `not_running`/`boot_failed` to `MachineNotRunningError`.

Two more worth stating because they are silent: `last_used_at` is written to disk on every
connection and every exec (C1), and image layers are held twice in RAM during a build (C2).

## A. Hacks, tricks and workarounds in production paths

### A1. Should fix before real servers: tenant id goes into a file path unvalidated
`crates/briqyardd/src/machine.rs:947-949`, `:608`, `:703`
```rust
if req.tenant.is_empty() || req.tenant.len() > 64 {
    return Err(invalid("tenant is required (at most 64 characters)"));
}
...
self.inner.store.put("tenants", id, &t)?;      // state/tenants/<id>.json
self.inner.store.delete("tenants", id)?;
```
`tenant: "../../etc/cron.d/x"` writes `state/tenants/../../etc/cron.d/x.json` as root, and
`DELETE /v1/tenants/../..%2Fsomething` removes a file. The id also lands in the fleet registry and
in log fields. Only the bearer token stands in the way. Clean version: validate the tenant like a
name (`valid_name`-style charset, or `[a-z0-9_-]{1,64}`) at the API boundary, in one place
(`briqyard-api`), and have `Store::path` refuse any key containing `/`, `..` or starting with
`.` as a second line.

### A2. Should fix before real servers: `tap_name` drops a character of entropy and reuses a colliding TAP silently
`crates/briqyardd/src/netw/mod.rs:122-130`, `host.rs:63-71`
```rust
let id: String = machine_id.chars().filter(|c| *c != '-' && *c != '_').take(12).collect();
format!("t{id}")   // "m_abcdef123456" -> "tmabcdef12345": the 'm' counts, the last hex digit is lost
```
and `ensure_tap` treats an existing link as success. Two machines whose ids share the first 11 hex
digits get one TAP: the second Firecracker opens the same device and traffic crosses. 11 hex
digits is 2^44, so this is rare, but it is a silent isolation failure when it happens. Clean
version: strip the `m_` prefix explicitly, use all 12 hex digits (`t` + 12 = 13 chars, under
IFNAMSIZ), and make `ensure_tap` fail when the link exists and is not ours (or delete and
recreate, since a TAP is per boot).

### A3. Should fix before real servers: `host_ip()` shells out synchronously on every endpoint view
`crates/briqyardd/src/machine.rs:2322-2359`
```rust
fn host_ip(&self) -> Option<Ipv4Addr> {
    // Read once per call: cheap and always current.
    let out = std::process::Command::new("ip").args([...]).output().ok()?;
```
`endpoint_view` is called from `view()` for every endpoint of every machine, so `GET /v1/machines`
with N exposed machines spawns N `ip` processes with `std::process` (blocking the tokio worker
thread) inside an async handler. Clean version: resolve the advertise address once in
`Manager::new` (or at `Ingress::start`) and keep it in `Inner`; the operator's `ingress.advertise`
should be required in production anyway (see B1).

### A4. Should fix before launch: poll-with-sleep where a wait on a condition exists
- `crates/briqyardd/src/fc.rs:408-416`: 50 × 20 ms polling `firecracker.pid` after the API answers.
  The jailer writes the pid file before exec, so the API answering implies the file exists; one
  read, with an error if missing, is the primitive.
- `crates/briqyardd/src/machine.rs:1639-1641`: `exited.changed()` then `sleep(200ms)` before reading
  the console for the exit line. The watcher (`settle_exit`) already waits for the console to be
  fully written (`Process::wait` waits on the `stamp` tasks); await `e.settled.notified()` here
  instead of a fixed 200 ms.
- `crates/briqyardd/src/machine.rs:2070-2096`: `wait_running` polls `get()` every 200 ms. The
  entry has a `Notify` (`settled`); a `watch<state>` on the record would let `/wait` block.
- `crates/briqyardd/src/zfs.rs:132-145`: `wait_device` polls for the zvol node (15 s). Acceptable
  (udev is async), but `udevadm settle` or inotify on `/dev/zvol` is the primitive.
- `crates/briqyard-init/src/init.rs:173-184`: the orphan reaper is a 10–100 ms polling loop
  instead of a `SIGCHLD` handler. Fine for a minimal init; note it.
- `crates/briqyard-init/src/init.rs:738`: `sleep(50ms)` before reboot "to flush the console". The
  console is a pipe the daemon drains to EOF when Firecracker exits; the sleep does nothing.

### A5. Should fix before launch: `snapshot_live` derives the snapshot directory by string-matching a path
`crates/briqyardd/src/machine.rs:1816-1833`
```rust
let base = live.api.parent().map(|p| if p.ends_with("run") { p.parent()... } else { p.to_path_buf() })
let inside = |name| if self.jail_for(&rec).is_some() { PathBuf::from("/").join(name) } else { base.join(name) };
```
This re-derives what `fc::Process::inside`/`outside` already compute, by guessing from the socket
path. Clean version: `Live` carries the `chroot: Option<PathBuf>` and `dir`, and uses
`fc::inside_path`/`outside_path`.

### A6. Should fix before launch: exit status scraped from the serial console
`crates/briqyardd/src/machine.rs:1768-1770`, `:2527-2545`; `crates/briqyard-init/src/init.rs:77-84`
The init prints `[briqyard] exit code=N oom=B requested=R` and the daemon greps the last 8 MB of
the console for it. Both ends test the line format, so it works, but it is string parsing where a
structured channel exists (vsock). A guest that prints the same prefix to its console can forge
its exit status (`parse_exit_line` keeps the last match). Clean version: the init connects out on
vsock to a host port (Firecracker makes `vsock.sock_<port>` on the host side) and sends one
`exit` frame before `reboot`; the console line stays as a human trace only.

### A7. Nit: stale and duplicated doc comments in the provider
`packages/providers/src/briqyard.ts:449-451`
```ts
/** briqyard keeps no memory snapshot yet: a suspend is a stop, the next start a cold boot. */
/** A suspend keeps a memory snapshot: the next start resumes in well under a second. */
```
The first line is false now; drop it.

### A8. Nit: `recover()` marks a crashed-daemon leftover as `stopped (idle)`
`crates/briqyardd/src/machine.rs:366-372`. The reason is chosen so the next use wakes it, which
is a workaround for not having a "stopped by the host" reason. With the control plane deciding
sleep (`sleep: never`), an `idle` reason is a lie it will read. Add `stop::HOST` (or `daemon`)
and let `canWake`-style callers treat it as wakeable.

### A9. Nit: `new_token` falls back to all zeros
`crates/briqyard-fleet/src/bootstrap.rs:15-22`
```rust
if let Ok(mut f) = std::fs::File::open("/dev/urandom") { let _ = f.read_exact(&mut b); }
```
If the open or the read fails the host token is `0000…` and the fleet forwards with it. The
daemon already depends on `rand`; use `rand::thread_rng().fill_bytes` and never ignore the error.

### A10. Nit: `sleep` stored as empty string for "never"
`machine.rs:1001-1005`, `:2019`, `:743-747`. "never" is encoded as `""` on disk and decoded back
on the way out. Store what the API says; one representation.

## B. Correctness and safety

### B1. Blocker: the host ingress and API are public on a server with a public address
- `crates/briqyardd/src/config.rs:202`: `bind: "0.0.0.0"` default for TCP endpoints.
- `hack/bootstrap-host.sh:75`: writes `listen: 0.0.0.0:7420`, and `http: 0.0.0.0:8080`.
- `crates/briqyardd/src/ingress.rs:154-163`: `proxy_tcp` dials the machine with no check at all.
- `SECURITY.md` says "bind a private address or firewall the port range", but nothing enforces it.

On briq, "the router is the only public entry, and that is what makes `token` mean anything"
(monorepo `CLAUDE.md`). With this provider, `exposePort` opens `0.0.0.0:200xx` on the host: a
`private` briq's HTTP port and a Postgres port are reachable from anywhere by port scan, with no
token, no TLS, no password gate for HTTP. The API on 7420 is plain HTTP with a bearer: the token
crosses the internet in clear on every control-plane call, and the heartbeat sends the daemon's
token to the fleet the same way (`heartbeat.rs:25`).

Clean version, in order of cost:
1. The daemon refuses to start when `ingress.bind` or `listen` is a non-loopback, non-RFC1918
   address and `ingress.allow_public: true` is not set. Same for `ingress.http`.
2. The router/edge reach the hosts over a private network (WireGuard is already the plan in
   `MESH.md`; the edge gets a peer). `ingress.advertise` becomes the WireGuard address.
3. Until then, the bootstrap installs an nftables input rule limiting 7420, 8080 and 20000–29999
   to the control plane's addresses. The daemon owns `table inet briqyard` already; add an input
   rule set `allowed_clients` the operator fills from the config.

### B2. Blocker: transitions are cancelled by a client disconnect
`crates/briqyardd/src/api.rs:200-205` (every handler awaits the manager directly),
`crates/briqyardd/src/image.rs:141-164`, `crates/briqyardd/src/machine.rs:1092-1118`, `:1442-1668`.

axum drops the handler future when the connection closes. Concrete consequences:
- `Builder::ensure` inserts a `Notify` into `building`, awaits `ensure_locked`, then removes it.
  Dropped mid-pull, the entry stays: every later `ensure` of that key does `n.notified().await`
  forever. The provider's create timeout is 130 s (`briqyard.ts:57`); a first pull of a large
  image on a slow host exceeds that. After one such timeout, that image is unusable until the
  daemon restarts.
- `start_entry` dropped after `fc::Process::start` and before the watcher is spawned leaves a
  Firecracker with the record in `starting` and `pid` possibly 0; the `boot_gate` permit is
  released, nothing settles it until a restart sweeps it.
- `create` dropped between `add_machine` and `save` leaves an in-memory entry with no record and
  disks half made; `name_taken` then refuses the name until restart.

Clean version: the manager runs each transition in a spawned task keyed by machine (a per-entry
job slot or a small per-machine queue, like the monorepo's `requestJob`); handlers do
`tokio::spawn(...)` and await the `JoinHandle`, so cancellation of the request only cancels the
wait. `Builder::ensure` wraps the removal in a drop guard regardless.

### B3. Should fix before real servers: boot failures answer 500 and are inconsistent between `create` and `start`
`crates/briqyardd/src/machine.rs:1460-1474` (`fail` → `MError::Other`), `:1633`, `:1641`,
`:1112-1117` (create swallows the start error and answers 201 with `state: error`),
`api.rs:78` (`Other` → 500). A `POST /start` on a machine whose process exits at boot is a 500
`internal`, with `tracing::error!` in `AppError::from` (api.rs:84-86), so every bad image is an
operator-level error line. See E1 for what the provider does with it. Clean version: a new
`MError::BootFailed(String)` → 409 (or 422) with code `boot_failed`; `create` with `start: true`
answers the same status as `start` would, with the machine in the body.

### B4. Should fix before real servers: the forward chain's default policy is accept, so a guest can send with a spoofed source
`crates/briqyardd/src/netw/nft.rs:20-37`
```
chain forward { type filter hook forward priority 0; policy accept;
    ct state established,related accept
    ip saddr <range> ip daddr <range> drop
    ip saddr <range> ip daddr { 10/8, 172.16/12, 192.168/16, 100.64/10, 169.254/16 } drop
    ip saddr <range> oifname "<egress>" accept
    iifname "<egress>" ip daddr <range> drop
```
Every rule keys on `ip saddr <range>`. A guest that sets its interface to any address outside the
range (it is root in its VM) matches none of them and is forwarded by policy, unmasqueraded: a
spoofed-source packet leaves the host on the egress interface. That is the classic "our hosts are
a DDoS reflector" problem, and it is also how a guest reaches the host's private networks if its
address is outside 10.64/10. Clean version: `policy drop` on forward, explicit accepts only, and
per-TAP source pinning (`iifname "tXXXX" ip saddr != <machine ip> drop`, or `ether saddr` pinning
in a bridge-family table) rendered from the machine list the same way bridges are. Also add a rule
for IPv6 (`meta nfproto ipv6 iifname "by*" drop`): the table is `inet` but every rule is `ip`.

Plausible, verify by `lsmod | grep br_netfilter` on the real servers: if `br_netfilter` is loaded
(Docker loads it), bridged intra-tenant traffic also traverses the `forward` hook and the first
`ip saddr <range> ip daddr <range> drop` rule breaks machine-to-machine traffic inside a tenant.
The e2e suite would catch it on such a host, but the rule should be `iifname != oifname` scoped
(drop only between different bridges) to be correct either way.

### B5. Should fix before real servers: `recover()` kills a pid it has not verified
`crates/briqyardd/src/machine.rs:355-364`
```rust
if rec.pid > 0 {
    unsafe { libc::kill(-(rec.pid as i32), libc::SIGKILL); libc::kill(rec.pid as i32, libc::SIGKILL); }
}
```
After a daemon crash and a host reboot (or a long downtime), `rec.pid` may belong to any process;
this SIGKILLs it and its process group as root. `adopt()` checks `/proc/<pid>/comm` but only when
the state was `running`; `starting`/`stopping` skip the check. `adopt` also checks only `comm ==
firecracker`, not that the `--id` matches this machine. Clean version: one `is_our_firecracker(pid,
id)` that reads `/proc/<pid>/cmdline` for `--id m-<id>` (the function `firecracker_processes()`
already parses that), used by `recover`, `adopt`'s poll, and `sweep_orphans`.

### B6. Should fix before real servers: `destroy` is not one critical section
`crates/briqyardd/src/machine.rs:1961-2006`. `stop_entry` takes and releases the entry lock; the
state is set to `destroying` under a second lock; the zvol destroy and the record delete run with
no lock. Between the stop and the `destroying` write, a `start` (or the restart-after-exit task,
`:1753-1763`, or an ingress wake) can take the lock and boot the machine; `destroy` then deletes
the TAP under a running Firecracker and `zfs destroy -r` fails "busy" for 10 s, leaving the
machine in `destroying` with a live process. Nothing retries a failed destroy until the next daemon
restart (`recover`). Clean version: `destroy` holds the entry lock from the state check to the
record delete (stop inside it, as `stop_entry` already allows with a flag), the restart task
re-checks the state under the lock (it does) *and* `destroying` is a terminal guard in `start_entry`.
Add a periodic pass that resumes `destroying` records.

### B7. Should fix before real servers: `start_entry`'s capacity check is not atomic
`crates/briqyardd/src/machine.rs:1445-1452`. `usage()` is read, then the state is set to
`starting` in a separate lock; N concurrent starts all pass with the memory of one. The
`boot_gate` semaphore limits concurrency of boots, not the sum of memory. Clean version: reserve
under one lock (a `Mutex<u32>` of committed memory in `Inner`, incremented when the state goes
to `starting`, decremented in `settle_exit`/`fail`), and the same for the fleet (B12).

### B8. Should fix before launch: fork snapshots on the source are never removed
`crates/briqyardd/src/machine.rs:1184-1195`, `:1981-1995`. A fork makes `source@fork-<id>` and
clones it. When the *fork* is destroyed, `release_clones` promotes clones of the fork's own
snapshots and `zfs destroy -r m/<fork>` removes the clone; `source@fork-<id>` on the source stays
forever, pinning every block the source has since rewritten. `s_*` snapshots from
`POST /snapshots` are never pruned either (no delete endpoint). On a long-lived Postgres briq that
is forked often (branches), this is unbounded disk growth. Clean version: on destroy of a machine
whose root was cloned from `X@fork-<id>`, destroy that snapshot when `clones` is empty (the
`origin` property names it: `zfs get origin`); add `DELETE /machines/{id}/snapshots/{snap}`.

### B9. Should fix before launch: state files, config drives and console logs are world-readable and hold secrets
`crates/briqyardd/src/store.rs:31` (`std::fs::write` → 0644 under umask 022),
`machine.rs:2759-2768` (`config.tar` 0644, hard-linked into each jail root at `fc.rs:505-514`),
`main.rs:77` (`/var/lib/briqyard` 0755). Every tenant's `env` (the control plane sends resolved
secrets, `briqyard.ts:263`) is readable by any local uid on the host, including the uid of every
other machine's Firecracker (chroot and seccomp stop Firecracker itself, but not a local account).
Backups include the record too (documented). Clean version: `umask(0o077)` at daemon start, create
`data_dir`/`state`/`run`/`jail` with 0700, write records and drives with `OpenOptions::mode(0o600)`,
and chown the jail copy of the drive 0400 to the jail uid.

### B10. Should fix before launch: unclamped durations from the request can panic the handler
`crates/briqyardd/src/machine.rs:2156` (`Duration::from_millis(timeout_ms + 10_000)`: u64
overflow, panics in debug, wraps in release), `:1886` and `:1943` (`timeout + Duration::from_secs(15)`:
`Duration::add` panics on overflow in every profile, with `timeout_sec: u64::MAX` from
`StopRequest`). axum has no `CatchPanic` layer here. Clamp `timeout_ms`, `timeout_sec`,
`grace_sec` and `limit` at the API boundary (the `/wait` handler already does: `clamp(1, 600)`).

### B11. Should fix before launch: `Manager::subnet` panics on a narrowed range
`crates/briqyardd/src/machine.rs:572-577`: `.expect("subnet index in range")`. An operator who
changes `network.range` to a smaller prefix after tenants exist crashes the daemon at the first
`view()`; `Manager::new` should refuse to load a tenant whose index is out of range with a message.

### B12. Should fix before launch: fleet placement does not reserve capacity and pins the tenant before the create lands
`crates/briqyard-fleet/src/main.rs:626-654`, `registry.rs:212-236`. `place()` reads `used` from the
last heartbeat (15 s old) and pins the tenant to the emptiest host. A burst of creates all land
on the same host until its heartbeat catches up; when the daemon answers 503 `capacity`, the
provider reads it as `ProviderUnavailableError` (5xx), the control plane retries, and the retry
lands on the same host because the tenant is now pinned. A tenant can be stuck on a full host.
Clean version: `place` adds `need_mb` to `used` in the registry until the next heartbeat; a
`capacity` answer from the daemon on a tenant's *first* machine unpins it; and the daemon's
`capacity` should be a 4xx-class code the provider does not treat as unavailability (see E1).

### B13. Should fix before launch: the fleet registry save swallows errors
`crates/briqyard-fleet/src/main.rs:41-49`
```rust
if let Ok(data) = serde_json::to_vec_pretty(&reg) { ... if std::fs::write(&tmp, data).is_ok() { let _ = std::fs::rename(...); } }
```
A full disk or a permissions problem makes every save a silent no-op; after a restart the fleet
forgets ordered hosts and their tokens (`token` lives only there). Log at `error` at least; return
the error from `register_host`/`order_host`.

### B14. Should fix before launch: fleet trust model
- `main.rs:202-207`: anyone with the shared `host_token` can `register` any URL under any id and
  the fleet will forward tenant requests (with env secrets) to it, authenticating with the token
  the attacker supplied. One compromised host can impersonate every other.
- `main.rs:207`: the bearer comparison is `!=` (not constant time; the daemon has `constant_eq`).
- `bootstrap.rs:167`: `StrictHostKeyChecking=accept-new` to a freshly delivered IP, carrying
  `FLEET_TOKEN` and the host's API token in the remote environment.
Clean version: per-host registration credentials (the token the bootstrap gave it, already in
`HostRec.token`, is what the heartbeat should present), an allowlist of expected addresses for
registration, and host-key pinning from the provider's API where it exists (Scaleway and OVH
expose it), else a first-connect fingerprint written into the host note for the operator.

### B15. Nit: `stop_entry` on a `stopping` machine registers its wait after releasing the lock
`crates/briqyardd/src/machine.rs:1883-1890`. `settled.notified()` is created after `drop(_guard)`
without `enable()`; if the watcher settles in between, the caller waits `timeout + 15 s` for
nothing. The suspend branch below (`:1913-1915`) does it right; do the same here. The init has the
same pattern in `shutdown` (`init.rs:855-859`): `main_done.notified()` is created after the
SIGTERM.

### B16. Nit: `/metrics` and `/v1/openapi.yaml` require the bearer
`api.rs:125`. Only `/healthz` is exempt; a Prometheus scrape needs the full API token. Give
`/metrics` its own token or exempt it on a loopback-only listener.

### B17. Nit: the HTTP ingress trusts the first `Host` header and has no connection limit
`ingress.rs:165-205`. Fine for v0; note that `hosts` is keyed by a label with 4 random hex
characters (`machine.rs:2407`, 65k possibilities) when the control plane does not name one — the
briq provider uses TCP endpoints only, so this is not on the critical path.

## C. Design choices that will hurt at scale or on real hardware

### C1. Should fix before real servers: a disk write per connection and per exec
`crates/briqyardd/src/machine.rs:2035-2038`, called from `machine_addr` (`:2443`, every ingress
connection), `exec` (`:2168`), `put_file`, `get_file`, `wake`. `touch_entry` sets `last_used_at`
and calls `save()`: a serialize + `write` + `rename` of the record. A Postgres briq with a
connection pool cycling, or an HTTP endpoint under load, turns into thousands of record rewrites
a minute on the host's root disk, each also bumping `updated_at` (which the provider reports as
`changedAt`, see E4). Clean version: `last_used_at` lives in memory (an `AtomicI64` on the entry),
is written with the next state change, and a 30 s timer flushes dirty entries; the sleeper reads
memory. The `Record` on disk then means "what the machine is", not "when it was last touched".

### C2. Should fix before real servers: an image pull holds every layer in memory, twice
`crates/briqyardd/src/image.rs:248-251`, `:328-347`. `oci_client::Client::pull` returns
`ImageData` with each layer as `Vec<u8>`; `ordered_layers` clones them all. A 2 GB image costs
4 GB of daemon RSS during the build, concurrent with guests. Clean version: `pull_blob` each layer
to a file under `extract-<key>/layers/` (streaming), then `apply_layer` from the file; memory is
bounded by the decompressor's buffer.

### C3. Should fix before real servers: memory snapshots land on the root filesystem
`crates/briqyardd/src/fc.rs:297`, `machine.rs:1840` (`snap.mem` written in the jail root, which
is `data_dir/jail/...` on the host's `/`). A suspended 32 GB machine writes 32 GB to `/`; with
`suspend_on_sleep` and the shutdown path (`close()` suspends every running machine) a host with
200 GB of guests needs 200 GB free on its root disk. Clean version: `jail_dir` on a ZFS
filesystem dataset of the pool (`byard/jail`, created in `Zfs::new`), or a per-machine
`byard/m/<id>/snap` zvol; the bootstrap sets `jail_dir` accordingly.

### C4. Should fix before real servers: the bootstrap installs whatever is latest
`hack/bootstrap-host.sh:46-57`: Firecracker from `releases/latest`, a guest kernel found by
listing the Firecracker CI bucket and taking the last version. Two hosts bootstrapped a week
apart run different Firecracker and kernel builds; a memory snapshot is tied to the Firecracker
version that wrote it (a restore-on-another-host plan would break); the CI kernel config is not
ours and can change. Pin `FIRECRACKER_VERSION` and `KERNEL_URL`/`KERNEL_SHA256` in the script (or
in the fleet's `bootstrap` config, passed through the environment like the others), and host the
kernel yourselves.

### C5. Should fix before launch: the nftables input chain grows four rules per tenant
`crates/briqyardd/src/netw/nft.rs:40-47`, re-rendered and reloaded on every tenant create/delete
(`machine.rs:614`, `:704`). Every packet to the host walks the list; at 1,000 tenants that is
4,000 rules. Clean version: one named set `tenant_bridges` of interface names and four rules
(`iifname @tenant_bridges udp dport 53 accept`, ...); tenant changes become `nft add element`
rather than a full table reload.

### C6. Should fix before launch: tenant → host pinning has no escape hatch
`registry.rs:107-113`. A tenant lives on one host for life ("machines do not move between hosts").
Fine for v0, but a drained host keeps its tenants forever, and B12 shows a tenant can be stuck on
a full host. Backups + restore already give you a move; the registry needs `POST /tenants/{id}/move`
or at least an unpin, and the briq side needs the `region`/host to be re-readable from the
machine (`host` is already added to the body).

### C7. Should fix before launch: the fleet scans every host for endpoints
`main.rs:898-922`, `:734-754`. `by_endpoint` forwards to every ready host until one does not
404; `list_endpoints` silently drops hosts that fail (a partial listing, unlike `list_machines`
which is correctly all-or-nothing). Index endpoints → host at create time like machines, and make
`list_endpoints` fail on a failing host.

### C8. Should fix before launch: `cgroup` path for stats is a hard-coded jailer default
`machine.rs:856`: `/sys/fs/cgroup/firecracker/<id>`. Pass `--cgroup-parent`/`--parent-cgroup`
explicitly in `fc.rs` and derive the stats path from the same constant.

### C9. Nit: the DNS forwarder opens a UDP socket per query and the resolver is per-tenant task
`netw/dns.rs:111-127`, `:64-75`. Fine to 10k tenants; a shared upstream socket with a request map
is the usual primitive when it matters.

### C10. Nit: the sleeper stops idle machines one after another
`machine.rs:2057-2066`. Each stop can take 25 s; a tick with 20 idle machines takes minutes.
Spawn per machine (bounded).

### C11. Nit: one `oci_client::Client` per `ensure`
`image.rs:132`. A new connection pool and TLS session per create. Keep one on the `Builder`.

### C12. Nit: `list_taps` deletes any 13-character `tun` link starting with `t`
`machine.rs:438-447`. On a dedicated host it is fine; a distinctive prefix (`bt…`) would make it
safe anywhere.

## D. Test quality

### D1. Should fix before launch: an e2e check that cannot fail
`hack/e2e.sh:35`
```sh
check "exit code" '! briqyard machine exec "$A" -- sh -c "exit 3"; [ $? = 3 ] || true'
```
After `! cmd`, `$?` is the negation (0), `[ 0 = 3 ]` is false, `|| true` makes the check pass.
Write `briqyard machine exec ... ; [ $? = 3 ]` with `set +e` around it, or capture the exit code
into a variable.

### D2. Should fix before launch: timing-based steps in the e2e suite
`hack/e2e.sh:63`, `:134`, `:146` (`sleep 2/3` to let a counter advance or a suspend settle). They
pass on a fast VM and will flake on a loaded host. Replace with waits on a condition (poll the
counter file, poll `suspended: true`), the way the `pg_isready` loops already do.

### D3. Should fix before launch: no contract test between the TypeScript adapter and the Rust API
`packages/providers/src/briqyard.test.ts` pins the request shapes the adapter sends against a
stub it wrote itself; `crates/briqyard-api/src/types.rs` tests the Rust side against its own
JSON. Nothing checks that `YardMachine`/`YardEndpoint` in `briqyard.ts:61-85` match
`api::Machine`/`api::Endpoint`, or that `api/openapi.yaml` matches either. A renamed field
(`stopped_reason`, `machine_host`) breaks silently. Clean version: generate the TS types from
`api/openapi.yaml` (or validate the stub's bodies against it with a JSON-schema check in the test),
and run `briqyard-spike.ts` in briqyard's CI against a real daemon once a KVM runner exists.

### D4. Should fix before launch: coverage holes on the risky paths above
Not covered by any suite: client disconnect during create/start (B2), concurrent start vs destroy
(B6), concurrent starts past capacity (B7), a tenant id with `/` or `..` (A1), nft with a spoofed
source (B4), a fleet save failure (B13), a `capacity` 503 followed by a retry (B12). The stress
driver (`hack/stress.py`) and `stress-invariants.sh` are the right place for the first three;
`cargo test` for the rest (the `Manager` has no unit tests at all: `machine.rs` tests only pure
helpers, 3238 lines with no test of `create`/`start`/`stop` against the fake `Zfs` and a fake
`fc::Process`). A `MockRuntime` trait for Firecracker (start/kill/wait) would make `Manager`
testable the way `Zfs` already is.

### D5. Nit: fleet tests assert the host id the registry picked for a static host
`crates/briqyard-fleet/src/tests.rs:375-399` and similar are fine. One thing to keep an eye on:
`a_listing_adds_the_host_and_is_never_partial` is the behavior the control plane depends on
("`Provider.list` must throw, never return `[]`"); keep it when the fleet gains an index.

## E. The provider branch against the monorepo's rules

### E1. Should fix before real servers: 5xx from the daemon is always "provider unavailable"
`packages/providers/src/briqyard.ts:169-242` (`failed = res.status >= 500 || 429` →
`ProviderUnavailableError`), `:359-387` (only `exec` maps `not_running` to
`MachineNotRunningError`). Combined with B3: an image that exits at boot makes `start` answer
500, the provider throws `ProviderUnavailableError`, the control plane answers 503, keeps the
pending state and retries (`CLAUDE.md`: "when the provider could not answer ... the pending state
is kept"), and `failureLevel` logs it as ours. The daemon's 503 `capacity` gets the same
treatment. Clean version: once B3 lands, map `not_running`, `boot_failed` and `capacity` codes to
`MachineNotRunningError`/a new `CapacityError` in `req` (by `code`, not by status), and keep
`ProviderUnavailableError` for connection failures, timeouts, 502/503 from the fleet
(`host_down`, `host_unreachable`) and 5xx `internal`.

### E2. Should fix before real servers: delivery bypasses the router's guarantees (B1 seen from briq)
`briqyard.ts:490-511`, `apps/router/src/router.ts:54-66` (`proxyTarget`), ADR 0015 "Delivery".
The router's `private`/`token` check only matters if nothing else reaches the port. The ADR's
consequence ("a router in `proxy` mode on a network that reaches the hosts' ingress addresses")
must say: a private network, and the hosts' ingress bound to it. Until then the branch should
not run staging. The branch should also carry the rule in `CLAUDE.md` ("Never allocate a public IP
to a team app") as: "on briqyard, the host's ingress bind is that public IP".

### E3. Should fix before launch: `exposePort` is now called on every provider in the create job
`apps/api/src/services/briqs.ts:1825-1837`. For every `publish` at create, the job calls
`s.provider.exposePort(h, port)` after `waitReady`. On Fly that is an extra `GET machine` per
create (`fly.ts:1275-1292`), and it is the control plane compensating for a provider that cannot
return the address from `create`. Clean version: `CreateInput` carries the port to publish (it
already knows `deliveryPort(spec)`) and `ProviderHandle` (or the `create` result) carries
`deliveryAddress?`; Fly returns none, briqyard returns the endpoint it made during the create.
One call, no provider-specific branch in the job.

### E4. Should fix before launch: `changedAt` is `updated_at`, which moves on every touch
`briqyard.ts:513-529`: `changedAt: m.updated_at`. With C1, `updated_at` changes on every
connection and exec, so drift's "state changed at" is never older than the last use. If
`drift.ts` uses `changedAt` to decide whether a provider state is stale vs a job in flight, a busy
briq always looks freshly changed. Clean version: the daemon exposes `state_changed_at` (set only
where `state` is written) and the provider reads that.

### E5. Should fix before launch: the cost rate is a code constant converted at a dated ECB rate
`briqyard.ts:131-152`: `usdPerGbMonth ?? 2.84` ("a Hetzner AX102-1 ... at the ECB rate of
2026-10-16"), and `apps/api/src/services.ts:47-54` never passes it, so the constant is what runs.
`CLAUDE.md`: "There is no exchange-rate constant anywhere". The costs page is in USD because Fly
bills in USD; our servers bill in EUR. Clean version: `BRIQYARD_EUR_PER_GB_MONTH` in env (per
environment, since staging and production will have different servers), converted through the
same `exchange_rates` table the pricing uses, or make `ProviderCosts` currency-aware.

### E6. Nit: `fork` without a volume is a plain create
`briqyard.ts:309-322`. briqyard clones the root disk on every fork (`machine.rs:1184-1195`), so a
fork of a volume-less briq could keep what the agent wrote to the root. Matching Fly's semantics
is a defensible choice (`forkCopies = 'disk'`); say so in the comment, since the daemon can do more.

### E7. Nit: `internalHost` is a name the router cannot resolve
`briqyard.ts:158-166`: `internalHost: m.machine_host` (`m_1.vm.internal`, resolvable only on the
tenant's bridge). The router falls back to `internalHost:port` when `deliveryAddress` is null
(`router.ts:64`), which on briqyard is a dead address. Harmless today because every briqyard
expose returns an address; make the fallback an explicit refusal (`decide` answers an error) when
the provider is briqyard, or carry a `requiresDeliveryAddress` flag.

### E8. Checked and fine
- `list` throws on any failure (`req` rejects) — rule kept.
- Every call has `AbortSignal.timeout`; retries are bounded (3) and only for GET/DELETE and for
  429/5xx; a POST that got no answer is never repeated — rule kept.
- No logging in the adapter; `onCall` reports each request with `requestId` — rule kept.
- Migration 0036 is one nullable column with no backfill — fine pre-launch.
- `exec-scripts.ts` extraction removes a real duplication between Fly and briqyard — good.
- `delivery-address.test.ts` covers the three paths (expose, publish at create, TCP) through the
  real API with a spied provider — good.

## What is genuinely well done; keep it

- **Record written last, atomically; orphans swept at start** (`store.rs`, `machine.rs:396-475`).
  A crash at any point leaves either a record with its resources or resources with no record,
  and the sweep handles the second. This is the right invariant; `stress-invariants.sh` checks it
  from outside. Keep both.
- **The config drive** (`machine.rs:2680-2755`, `init.rs:285-324`): a tar the init reads raw, no
  host mount of a guest filesystem, secrets never in the API's answers. Keep.
- **Image extraction** (`image.rs:465-621`): `secure_join`/`secure_join_nofollow`, whiteouts,
  devices skipped, hard links resolved inside the root, and the tests that feed it hostile
  archives. Keep; just stream the layers (C2).
- **The jailer integration** (`fc.rs:292-346`): one uid per machine derived from the network
  position, cgroup limits from the size, `--new-pid-ns`, files placed into the chroot by hard
  link. Keep.
- **The per-machine `tokio::sync::Mutex` for transitions plus the `settled` Notify** is the right
  shape; B2 and B6 are about where the lock is taken, not the design.
- **`Zfs` with a fake binary in tests** (`zfs.rs:342-676`): the fake speaks the real error
  strings, every call is recorded. This is the pattern to copy for Firecracker (D4).
- **Backups as `zfs send` chains to an object store with the record beside them**, restore as a
  create: simple and host-independent. Keep.
- **`wait_ready` through vsock ping, exec with process groups, the orphan reaper that never
  steals a tracked child's status** (`init.rs:170-217`): correct PID-1 behavior, tested.
- **Fleet placement as pure functions** (`registry.rs`): testable, and the "a listing is never
  partial" rule is exactly what the control plane needs.
- **`hack/stress.py` + `stress-invariants.sh`**: the crash-mid-run mode found real bugs; keep it
  as the gate for B2/B6/B7 fixes.
- **The provider's `req()`** is a faithful copy of the Fly adapter's discipline (deadline, bounded
  retry, `onCall`, request ids). Keep; fix the status→error mapping (E1).
