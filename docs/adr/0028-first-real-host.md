# ADR 0028: A real host: the pool mirrored on the OS's disks, a server added by hand, the API on the private network

Date: 2026-10-21 · Status: accepted; amends ADR 0007 (the OVH install), ADR 0013 (a host added by hand is bootstrapped and pinned like an ordered one)

## Context

Everything ran on arm64 Lima VMs with a file-backed pool and one interface. The first real hosts are OVH dedicated servers: x86_64, two NVMe disks that OVH's installer puts the OS on in software RAID, a public interface and a vRack (a private layer-2 network between the servers). They are ordered in the OVH manager, not through the provisioner. The hosts' API, HTTP ingress and TCP endpoints carry tenants' secrets and traffic: they belong on the vRack, the public interface on nothing but SSH.

## Decisions

**The pool is one device, or two as a mirror.** `BRIQYARD_POOL_DEVICE=/dev/nvme0n1,/dev/nvme1n1`. A mirror because one NVMe dying is the commonest failure of a server, and on a stripe it is a host loss: every tenant back to its last backup (ADR 0008, 0023: up to `every` old), hours of restores. On a mirror nothing is lost and the disk is replaced online (`zpool replace`). The price: half the space, 860 GB usable on 2 × 960 GB after the OS. Backups still cover the host itself. More than two devices are refused: no server of ours has more yet.

**The OS on a small RAID 1, the rest of each disk left free; the bootstrap partitions the free space.** At install (OVH manager or `/reinstall`): `/boot` 1 GiB and `/` 100 GiB, ext4, RAID 1, no swap, nothing filling the disks. `/` is 100 GiB because image builds extract in `<data_dir>/images` on it, several at once (`boots_at_once`). No swap: memory is never overcommitted (ADR 0007), and a swapping host stalls every guest. A device is, for the pool:

| Device | Becomes |
|---|---|
| a partition | itself |
| a disk with nothing on it | itself (ZFS partitions it) |
| a disk with partitions (the OS on part of it) | a new GPT partition in its largest free space, labelled `briqyard-pool`, at least 10 GB; found by its label on a later run |
| anything mounted, swap, a RAID or LVM member, any filesystem, a pool not imported (a re-run with the pool exported, a reinstalled OS) | refused, with what it holds (`zpool import byard`, or `wipefs -a` it if it is meant for the pool); `zpool create` overwrites nothing, `-f` only for a mirror of two sizes |

The new partition is added to the running kernel alone (`partx -u`): the OS's partitions stay in use. Members are named by `/dev/disk/by-partuuid/`: NVMe names can change order across reboots. The same works on any provider whose installer can leave space free.

**A server bought by hand is added through the fleet and bootstrapped as an ordered one.** `briqyard host add <ssh address> --address <API address> [--region R]` (`POST /v1/hosts`) records the host `provisioning`, provider `manual`, with a fresh token and nothing pinned: the same loop (`bootstrap::to_install`) runs the same script over SSH, pins the SSH key at the first success and the API certificate over the pinned key (ADR 0013, 0020), and the host turns `ready` at its first heartbeat. Its SSH address (`HostRec.ssh`, `ssh:` in `host ls`) may differ from its API's: SSH reaches the public address, the API lives on the vRack. A retire forgets it once empty; the provider has nothing to release. Refused: the bootstrap off (409 `bootstrap_off`), an id or address the fleet has (409 `conflict`), an API address that is not IPv4, or apart from the SSH address and outside `private_network` (400).

**On the private network: the API, the ingress and the endpoints bind the vRack address, the public interface takes SSH only.** The fleet's `provisioner.bootstrap.private_network` (`10.42.0.0/16`) names the vRack; a host whose API address is in it is given `PRIVATE_ADDRESS=10.42.0.11/16` (and `PRIVATE_INTERFACE`, `PUBLIC_TCP_PORTS`). The script puts the address on the interface when it is not there (netplan, `60-briqyard-private.yaml`), binds `listen`, `ingress.bind` and `ingress.http` to it (so endpoints are reported at it), advertises `https://<it>:7420`, and writes `allowed_clients` (the vRack, and the edge's addresses). The public interface (the default route's) gets `table inet briqyard_host`: established and related, ICMP, DHCP replies, SSH's own ports (`sshd -T`) and `public_tcp_ports` (an edge's beside the daemon, below), a counted drop for the rest; loaded by `briqyard-firewall.service` before the network at every boot, apart from the daemon's tables, which never touch it. Machines' egress still leaves by the default route's interface (`network.egress`, masqueraded): the forward chain accepts only `oifname <egress>`, so no tenant reaches the vRack (`the_forward_chain_drops_by_default`). Rejected: OVH's Network Firewall (stateless, 20 rules per IP, replies to the host's own DNS and NTP need rules of their own, and it is OVH's alone); the daemon owning the public rules (nothing while it is down or before it starts, and the host's SSH is not the daemon's); ufw (a second owner of nftables; it and `nftables.service` flush every table, so neither is ever enabled).

**The control plane's edge on the first host, beside the daemon.** Until the region has edge servers of its own, the edge (Caddy and the control plane's router, in Docker on the host's network) runs on the first host, 80 and 443 public. What that takes:

| Clash | Resolution |
|---|---|
| Two firewalls: nftables drops what any table drops, and the edge's own (policy drop on every interface) would close the vRack and the machines' DNS | One owner, ours: the edge's bootstrap writes none on a host with `/etc/briqyard/firewall.nft`, and refuses unless that firewall is in force and opens 80, 443 and the router's TCP listener ports; briqyard's bootstrap refuses when the edge's own table is loaded. The ports are the host's own (`host add --public-tcp-ports`, kept on its record, the fleet's `public_tcp_ports` as the default): a re-run of its bootstrap, or another host added, never changes them |
| Docker's iptables rules: started with forwarding off (a boot where it comes up before the daemon), it turns forwarding on and sets the forward policy to drop, and every machine loses the internet (measured with Ubuntu's docker.io 29.1.3: started after the daemon, policy accept and egress fine; started with forwarding off, policy drop and egress gone) | The edge's bootstrap writes `/etc/docker/daemon.json` (`iptables`, `ip6tables` false, `bridge: none`) before installing Docker: host networking needs none of it |
| Port 80: certbot's for the fleet's certificate, Caddy's for its redirects | The fleet listens on loopback with `tls: off`; Caddy serves its name with a certificate of its own by HTTP-01 (a site of the edge's): no certbot, no fleet restart at renewal. Every caller then arrives from loopback: the fleet reads a host call's caller from `X-Forwarded-For` on a loopback listener (ADR 0026), which must be the address of the host's record, its vRack one. A host dialing the fleet's public name would come from its public address and be refused, so each vRack host resolves the fleet's name to the fleet's vRack address (`provisioner.bootstrap.fleet_address`, `FLEET_ADDRESS`, a line in `/etc/hosts` the bootstrap writes) and Caddy serves the name on the vRack too. Rejected: the fleet trusting a host's token alone behind the proxy (ADR 0026 checks the address on purpose); a private DNS zone (one more service for one name) |
| The router dials this host's vRack address | Delivered over loopback, which the daemon's table always allows: `allowed_clients` need not list the host; machines still never reach the daemon |
| TCP endpoints resolve to this host, and the daemon drops what machines send it: no machine of the region could use one | `network.host_ports`: machines with egress `open` reach those ports at the host's addresses (never a tenant's `.1`, the one host address a `via` machine reaches), as the internet does; the bootstrap writes `PUBLIC_TCP_PORTS` there. Not counted as internet traffic, and on purpose not under the egress limits (connection rate, bandwidth): it never leaves the host |
| An endpoint stored outside the range (a range changed under it) would listen where the table keeps nothing for `allowed_clients` | Refused at start, naming the endpoint and the range, as a tenant outside `network.range` is |
| The edge's MongoDB listener (27017) sat in the endpoint range (20000-29999): the daemon's table drops the range for all but `allowed_clients`, so the internet could not reach it, and an endpoint could take the port. Found by the configuration check below, in the dev VM | The range is now `30000-32767`, Kubernetes' NodePort range: no well-known service's port, under the kernel's ephemeral ports; 2,768 endpoints a host. A host port inside the daemon's ports is refused at start |
| The edge's memory and CPU are not the machines' | `capacity.reserved_memory_mb` (default 2048, the 2 GB kept before) and `reserved_threads` (default 0), Kubernetes' `systemReserved`; this host keeps 3072 MB (the idle edge took 29 MiB in the dev VM, Docker and containerd 555 MB with their page cache: the rest is the edge's room under load) |

Rejected: a flag telling the edge to skip its firewall (detection by the file is the same and cannot be forgotten); the edge's table accepting the vRack and the bridges (two owners of one policy); certbot DNS-01 (a token that edits the product's DNS zone, on a host); the fleet on its own port with lego following a CNAME into the endpoints' zone (one more tool and timer); allowing machines every port of the host's addresses (the daemon's would be among them).

**The ZFS cache is capped: 10 % of memory, 1 to 16 GB (`BRIQYARD_ARC_GB`), and the daemon leaves the cap out of its capacity.** Ubuntu 24.04's OpenZFS 2.2 lets the ARC take half the memory (2.3: nearly all); the kernel reclaims it only when a guest faults its memory in, slowly, and the OOM killer's choice is a Firecracker. Default `capacity.memory_mb` is the host's memory less 2 GB and less `zfs_arc_max`. Rejected: `primarycache=metadata` on the zvols (guests cache their own data; worth measuring, not a day-one change).

**A private repository's release is read through GitHub's API.** `BRIQYARD_RELEASE_TOKEN` (fleet: `provisioner.bootstrap.release_token` or the fleet's environment; a fine-grained token, contents read on the repository) resolves each asset of `BRIQYARD_RELEASE`; every binary is checked against the release's `SHA256SUMS-<arch>` before any is installed. `host upgrade` (ADR 0027) passes the same token with the release, and nothing else of the host's. Release assets of a private repository are not served at their download URL. Rejected: the fleet copying its own binaries to the host (ties a host to the fleet's build and arch; how releases reach hosts is ADR 0027's).

**x86_64 needs no code of its own.** Checked: the release workflow names the files as the bootstrap fetches them (`<binary>-linux-x86_64`, `briqyard-init` static on musl, `SHA256SUMS-x86_64`); the pins match Firecracker's published digest (`firecracker-v1.17.0-x86_64.tgz.sha256.txt`) and the files downloaded on 2026-10-21 (the kernel an x86 ELF `vmlinux`, the arm one an `Image`); the boot arguments (`console=ttyS0 reboot=k panic=1 pci=off i8042.*`) are Firecracker's x86 ones and harmless on arm; the image platform follows `std::env::consts::ARCH`; no CPU template, which is right while memory snapshots never leave their host (backups and restores are disks only). Left to the real server: KVM on its CPU (Firecracker tests Intel Skylake and later, AMD Milan and Genoa; OVH's EPYC 4004 and Ryzen are Zen 4, close but untested upstream), a boot and a resume with the CI kernel, the jailer and cgroups v2 on a stock kernel, suspend and resume times off nested virtualization, the vRack interface's name, netplan on OVH's image, the install layout through the manager.

**The suites run against a remote host.** `hack/e2e.sh` takes `BRIQYARD_URL`, `BRIQYARD_TOKEN`, `BRIQYARD_TLS_FINGERPRINT` (its own curl calls trust the daemon's certificate once its SHA-256 matches, as the CLI does) and `BRIQYARD_INGRESS` (default the API's address, port 8080); it runs on the host or any Linux in the vRack: endpoints are vRack addresses, and it needs GNU tools. The fleet suites take `BRIQYARD_TOKEN` and run from anywhere that reaches the fleet; `fleet-smoke.sh` orders only through a dry-run provisioner and drains and forgets only a host of `hosts:`, so it leaves a real fleet's hosts alone.

**OVH's API against our provisioner (schemas read 2026-10-21).** Matches: the signature (`$1$` + SHA-1 of secret, consumer key, method, full URL with its query, body, timestamp), `/auth/time`, the cart (`POST /order/cart`, `/assign`, `/eco` or `/baremetalServers`, `/item/{id}/configuration`, `POST /checkout` with `autoPayWithPreferredPaymentMethod` and `waiveRetractationPeriod`), `/me/order/{id}/status` and its values, `/dedicated/server`, `/terminate`, `/install/status`. Fixed: `POST /install/start` is gone from the API: the install is `POST /dedicated/server/{name}/reinstall` with `operatingSystem`, the key's text as `customizations.sshKey` (read from `/me/sshKey/{name}`) and the layout above as `storage`; `/me/order/{id}/details` lists ids, each read at `/details/{id}`; a plan's mandatory options (memory, disks, bandwidth) are added, the cheapest of each family for a month. Still assumed, checked at the first real order: a delivered order's detail carries the server's name as `domain`; `dedicated_os: none_64.en` is accepted; the cheapest option per family is the plan's base configuration; `/install/status` answers 404 when no install runs. Dry run stays the default.

## Consequences

- A real host loses half its NVMe to the mirror and 101 GiB of each disk to the OS.
- The vRack address of an ordered OVH server is not known to the API: an ordered host keeps its public address for its API, as before, until the fleet allocates vRack addresses (`private_network` and the server's private MAC, `GET /dedicated/server/{name}/networkInterfaceController?linkType=private`).
- The first host carries the edge, so it is the region's single point of entry until edge servers of their own exist; they reach the hosts on the vRack (`allowed_clients`), an edge outside it needs the mesh (`MESH.md`).
- The fleet's bootstrap carries a GitHub token while the repository is private.
- A host's interface names come from one fleet-wide `private_interface`: another server model with other names gets its vRack address by hand first, which the script then finds and keeps.
- Reopen the mirror for servers with four disks or more (two mirrors striped), and the ARC cap with measurements of real workloads.
