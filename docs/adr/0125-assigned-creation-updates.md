# 0125: Assigned creation updates retain original process authority

An initial assigned process can receive a data-volume increase before a continuation
exists. Stopped assignments also accept a complete boot-file replacement. Neither
operation creates a historical run or changes the assignment receipt or creation reader.

Schema 3 update journals distinguish current-run, stopped-creation and live-creation
sources. Schema 1 and 2 retain their serialized bytes and validation rules. Creation
hash domains distinguish stopped and live sources. Live sources bind the original
process incarnation, complete bind acknowledgment, launch hold, intrinsic host and
exact disk GUIDs. Fresh owned process proof precedes live growth. The durable intent
and namespace quota reservation precede the external grow; retries reconcile the
same target and verify DATA identity before another growth or coalescing.

Before clearing the original PID or mapping, confirmed owned exit or a validated
host-boot change writes a bounded settlement witness and the exact cold stopped
projection. Repair and directory sync precede replacing an outstanding journal.
The original source remains immutable. Same-boot startup repairs backing and uses
existing assignment-aware process and guest continuity checks; it never relaunches.
Unknown evidence retains the journal, disks and reservation. An explicit cold start
consumes the settled target as sequence 1 with no previous-run hash. The permanent
receipt, creation reader and launch hold remain; update deletion follows durable run,
machine and continuation-reader agreement.

Stopped `files` replaces the complete list, `[]` clears it, and omission preserves
pending files. Explicit current files cancel an older pending replacement. Existing
pending application makes the next start cold. Clearing the list does not delete
paths written by a previous guest. Running file changes and root-swap coalescing
remain refused. Errors and events carry no file contents.

The independent `assigned-update-v3` capability and permanent protocol floor 4
fence managed installation, handover and automatic rollback. Unbound warm pools
remain disabled by default. Native lifecycle, crash and rollback qualification are
required before enabling them.
