# ADR 0032: The fleet's registry is backed up to the object store, encrypted with age to a key kept off the fleet's host

Date: 2026-10-21 · Status: accepted; follows ADR 0026

## Context

The fleet's registry (`<state_dir>/registry.json`) holds every host's token and, since ADR 0026, every host's pool key. Lost, each host keeps running until its next reboot and then cannot read its pool: its machines are gone but for their backups. ADR 0026 made this backup a blocker before any tenant on a real host. Kubernetes has the same need for etcd (`../KUBERNETES-MAP.md`, etcd backup).

## Decisions

**The fleet writes its registry to an object store, the one the hosts already use.** `backup: { store, endpoint, region, recipient }` in the fleet's config: `s3://bucket/prefix` or `file:///path`, credentials from `BRIQYARD_S3_ACCESS_KEY` and `BRIQYARD_S3_SECRET_KEY`, read the way a host reads its own. **The fleet's credentials are its own, never a host's**: the bucket's policy lets the hosts' key write `backups/` only and the fleet's key `fleet/` only, so a host's disk that leaves our hands cannot overwrite or delete the registry's backups; versioning is on, so an overwrite of `fleet/registry.json.age` keeps the previous one. A request's error never carries its presigned URL (it holds the access key id and a signature good for an hour): the store maps every client error without its URL, and the 503 a host gets says only that the backup failed. The store client moved from the daemon to its own crate, `briqyard-objstore`, shared by both: one way to talk to a store. Objects: `fleet/registry.json.age`, the newest, and `fleet/registry-<UTC day>.json.age`, the last of each day, kept (a registry is a few KB; deleting is the operator's, with the bucket's lifecycle rules).

**Written once a minute when it changed, and before a key is handed out.** The fleet compares the registry's SHA-256 with what it last wrote and writes only a change; heartbeats change `last_seen`, so that is about once a minute, two objects each time, 2,880 small writes a day at most (`last_seen` is kept in the backup: it is how a restore says how old it is). A write reads the registry once it has its turn, so a write that waited never lands an older registry over a newer one, and each object is given 30 s: a key request waits on it, and the store's client otherwise allows an hour. A host's pool key is served only once the store holds it (the last write had that host with that key): a new key is written to the store before it is answered, and a store that refuses the write answers the host 503 `backup`, so no pool is ever created with a key the backup lacks. A write that fails in the background is an `error` line and is tried again a minute later. Rejected: a write per registry change (one per heartbeat, every host, every 15 s); a write only when a key is made (tokens, pins and tenant placements would be a day old).

**Encrypted with age to an X25519 recipient; the identity is kept off the fleet's host.** `backup.recipient` is an `age1…` public key; its identity (the private key) is made with `briqyard-fleet keygen --out <file>` (or `age-keygen`, same format) on the operator's machine and kept offline. The fleet can write a backup and cannot read one, so a copy of the fleet's disk or of the bucket opens nothing. age (`age` crate 0.12, the format and tool by Filippo Valsorda): one recipient string in the config, authenticated encryption, a CLI any operator can use without us (`age -d -i key registry.json.age`). Its cost: 81 more crates in the lock file (292 to 373, besides briqyard-objstore): its localization, scrypt and the plugin protocol come with it, none of them in the daemon. Accepted for a well-known format and tool over code of ours. Rejected: a symmetric key in the fleet's config (on the host the backup protects against losing; a copy of its disk would open the backup); GPG (keyrings, many options, a large tool for one recipient); NaCl sealed boxes (the same primitive without a file format or a tool); S3 server-side encryption alone (the provider holds the key, and a `file://` store has none).

**`briqyard-fleet restore --identity <file> [--from <object>]` writes the registry back**, from `backup.store`, decrypted, parsed as a registry (a backup that does not parse is refused, as a registry file is, ADR 0026), `0600`, and only when there is no registry: it never writes over what a fleet wrote. It prints what the fleet will trust once started on it, for the operator to check first: each host's id, url, pin prefix, whether it has a token and a pool key, and the newest heartbeat in it (how old the backup is); never a token or a key. Then the fleet starts on it: hosts' tokens, pins and pool keys as of the backup. Placements made after the backup and before the loss come back from the hosts' heartbeats, as a fleet restart already does; a key made in that minute cannot be missing, since none is served unbacked. What a restore does not bring back from that last minute: a host ordered and not yet keyed (its token and, once bootstrapped, its pin: it is ordered again), a token rotated (the host's config has the new one: put it in the record by hand), a drain (drain again), a host retired or forgotten (it is back in the registry: forget it again).

## Consequences

- Restoring needs the identity: losing both the registry and the identity loses every key, as before. Keep the identity in two places off the fleet's host (a password manager and a printed copy).
- A store that is down stops new keys (a bootstrap creating a pool, a host whose key was made but not yet written) with 503 `backup`; a host whose key the store holds gets it as before.
- The backup holds every host's token as well: rotating a token (ADR 0026, a disk swapped) leaves the old one in older daily objects, readable only with the identity.
- The fleet itself is still one process with one file: this is a backup, not availability. Fleet HA (`../KUBERNETES-MAP.md`) stays open.
- Development: `hack/fleet-restore.sh` adds a `backup:` section to the dev fleet's config for its run, with an identity on the fleet's host (development only), backs up, loses the registry, restores it, and checks that `fc2`, its pool locked as a reboot leaves it, comes back with its key from the restored registry.
